01
Introdução

Por que precisamos do SOLID?

O desafio não é apenas fazer o programa funcionar hoje. É conseguir alterar uma regra amanhã sem modificar uma dezena de arquivos.

Antes de começar

O que você vai conseguir fazer

  • Identificar o motivo de mudança e a dependência que dificultam uma evolução.
  • Refatorar um checkout sem alterar os resultados esperados.
  • Explicar e verificar o contrato de implementações substituíveis.
  • Justificar quando uma abstração vale o custo.

Pré-requisitos: classes, interfaces, construtores, exceções e decimal em C#. Os trechos de cada princípio são recortes didáticos independentes; o laboratório é o programa completo.

Código difícil de evoluir

Uma única classe faz tudo

O sistema calcula descontos, salva pedidos, envia mensagens e imprime etiquetas dentro de um único método.

Resultado: cada mudança pode afetar várias funcionalidades não relacionadas.

Código organizado

Cada parte tem um papel claro

Validação, desconto, persistência e notificação possuem responsabilidades e contratos definidos.

Resultado: mudanças são mais localizadas e testes ficam mais simples.

Atenção: SOLID não é uma biblioteca, um framework nem um padrão obrigatório para qualquer classe. São princípios para orientar decisões de design, especialmente quando o código precisa evoluir.

S
Princípio 1

Single Responsibility Principle

Princípio da Responsabilidade Única (SRP)

“Uma classe deve ter apenas um motivo para mudar.”
S
Analogia: uma pequena loja

Imagine que a mesma pessoa é caixa, entregador e contador. Uma mudança no imposto, na entrega ou na forma de pagamento afeta seu trabalho. Separar funções dá clareza à operação.

ANTES · três motivos para mudar
A mesma classe valida, persiste e notifica.
public class PedidoService
{
    public void Finalizar(Pedido pedido)
    {
        if (pedido.Total <= 0)
            throw new Exception("Total inválido");

        Console.WriteLine("Salvando pedido");
        Console.WriteLine("Enviando e-mail");
    }
}
DEPOIS · papéis separados
O serviço coordena; cada dependência tem uma responsabilidade.
public class PedidoService
{
    private readonly ValidadorPedido _validador = new();
    private readonly PedidoRepository _repo = new();
    private readonly EmailConfirmacao _email = new();

    public void Finalizar(Pedido pedido)
    {
        _validador.Validar(pedido);
        _repo.Salvar(pedido);
        _email.Enviar(pedido);
    }
}
// Classes de apoio possuem suas próprias tarefas.
Quando usar?

Quando uma classe mistura regras de negócio, acesso ao banco, interface ou comunicação externa.

Não confunda

SRP não significa “uma classe com um único método”. Significa agrupar comportamentos que mudam pelo mesmo motivo.

Para você pensar

Se a empresa trocar o servidor de e-mail, qual classe deveria ser alterada?

Revelar resposta comentada

Idealmente, apenas a implementação responsável pelo envio de e-mail. O cálculo do pedido não deveria mudar.

Quem pede a mudança?

Regras comerciais mudam por decisão do negócio; persistência muda por decisões de infraestrutura; mensagens mudam por decisões de comunicação. Use esses motivos para avaliar coesão. Coordenar colaboradores pode ser uma responsabilidade coesa.

O
Princípio 2

Open / Closed Principle

Princípio Aberto/Fechado (OCP)

“Uma estrutura deve ser aberta para extensão e fechada para modificação.”
O
Analogia: controle de videogame

Você pode conectar novos acessórios usando uma entrada compatível, sem desmontar o videogame a cada novidade. Em software, isso significa criar pontos de extensão estáveis.

ANTES · regra crescente
Novo tipo de desconto exige editar o método existente.
public decimal Calcular(string tipo, decimal total)
{
    if (tipo == "vip")
        return total * 0.90m;

    if (tipo == "natal")
        return total * 0.80m;

    return total;
}
DEPOIS · extensão por estratégia
Novas classes implementam o mesmo contrato.
public interface IPoliticaDesconto
{
    decimal Aplicar(decimal total);
}

public class DescontoVip : IPoliticaDesconto
{
    public decimal Aplicar(decimal total)
        => total * 0.90m;
}

public class CalculadoraPreco
{
    public decimal Calcular(decimal total,
                            IPoliticaDesconto politica)
        => politica.Aplicar(total);
}
Quando usar?

Quando surgem frequentemente novos tipos de desconto, pagamento, relatório ou cálculo.

Não confunda

OCP não proíbe editar código. Ele sugere criar extensões onde existe variação recorrente e previsível.

Desafio rápido

Como criar um desconto de 25% sem alterar CalculadoraPreco?

Ver uma possível implementação
public class DescontoBlackFriday : IPoliticaDesconto
{
    public decimal Aplicar(decimal total)
        => total * 0.75m;
}
O que permanece fechado?

Neste exemplo, a calculadora permanece estável para novos descontos. O ponto de composição ainda muda para escolher a estratégia. Corrigir um bug ou revisar o contrato exige editar código: OCP não promete imutabilidade.

L
Princípio 3

Liskov Substitution Principle

Princípio da Substituição de Liskov (LSP)

“Uma implementação deve poder substituir outra sem violar o contrato esperado.”
L
Analogia: tomadas padronizadas

Dois carregadores que prometem o mesmo padrão devem funcionar sem surpresas. Se um deles exige uma condição secreta ou quebra o equipamento, não respeita a promessa de compatibilidade.

ANTES · promessa quebrada
A subclasse restringe entradas que a classe-base aceitava.
public abstract class Frete
{
    // Contrato: peso positivo => preço retornado.
    public abstract decimal Calcular(decimal peso);
}

public class FreteMoto : Frete
{
    public override decimal Calcular(decimal peso)
    {
        if (peso > 5)
            throw new NotSupportedException();

        return peso * 4m;
    }
}
DEPOIS · mesma regra para todos
Um contrato claro expressa indisponibilidade sem surpresa.
public interface IFrete
{
    // Peso positivo. null = serviço indisponível.
    decimal? Calcular(decimal peso);
}

public class FreteMoto : IFrete
{
    public decimal? Calcular(decimal peso)
        => peso > 5 ? null : peso * 4m;
}

public class FreteCaminhao : IFrete
{
    public decimal? Calcular(decimal peso)
        => peso * 8m;
}
Como o consumidor trata as duas respostas?

O contrato mudou para admitir indisponibilidade. Atualize os clientes; trocar apenas a interface não corrige o sistema inteiro.

IFrete[] opcoes = { new FreteMoto(), new FreteCaminhao() };
foreach (IFrete frete in opcoes)
{
    decimal? preco = frete.Calcular(8m);
    Console.WriteLine(preco is decimal valor
        ? $"Frete: {valor:C}"
        : "Serviço indisponível para este peso");
}
// Moto: indisponível. Caminhão: R$ 64,00.
Quando usar?

Ao trabalhar com herança e implementações de interfaces que serão usadas de forma intercambiável.

Não confunda

Compilar não prova LSP. Também é preciso preservar expectativas: entradas válidas, saídas, efeitos e falhas previstos.

Pergunta para a turma

Se um sistema recebe qualquer IFrete, pode assumir que todo cálculo sempre terá um preço?

Revelar resposta comentada

Não. O novo contrato permite null para indicar serviço indisponível. O consumidor deve tratar os dois resultados para qualquer implementação.

Contrato é comportamento

A implementação não deve exigir mais de quem chama nem garantir menos do que o contrato promete. Preserve também invariantes e efeitos observáveis. No frete, permitir null é uma mudança do contrato: todos os consumidores precisam passar a tratar a indisponibilidade.

I
Princípio 4

Interface Segregation Principle

Princípio da Segregação de Interfaces (ISP)

“Ninguém deve ser obrigado a depender de operações que não utiliza.”
I
Analogia: painel de uma máquina

O operador de uma esteira precisa de botões de ligar e parar. Um painel separado por tarefa evita que ele dependa de controles de impressora, solda e empilhadeira. A interface deve atender ao consumidor que a utiliza.

ANTES · métodos inúteis
O pagamento é forçado a oferecer operações que não fazem parte do seu papel.
public interface IOperacaoLoja
{
    void Pagar(decimal total);
    void EmitirEtiqueta();
    void RastrearEntrega();
}

public class PagamentoPix : IOperacaoLoja
{
    public void Pagar(decimal total) { /* ... */ }

    public void EmitirEtiqueta()
        => throw new NotSupportedException();

    public void RastrearEntrega()
        => throw new NotSupportedException();
}
DEPOIS · cada recurso tem seu contrato
A classe implementa apenas o que realmente oferece.
public interface IPagamento
{
    void Pagar(decimal total);
}

public interface IEtiqueta
{
    void EmitirEtiqueta();
}

public interface IRastreamento
{
    void RastrearEntrega();
}

public class PagamentoPix : IPagamento
{
    public void Pagar(decimal total) { /* ... */ }
}
Quando usar?

Quando clientes dependem de operações irrelevantes. Métodos vazios ou NotSupportedException em implementações podem indicar que o contrato reúne necessidades diferentes.

Não confunda

Não é necessário criar uma interface para cada método. Agrupe operações que fazem sentido para os mesmos consumidores.

Pergunta para a turma

Um sistema de rastreamento precisa conhecer o contrato IPagamento?

Revelar resposta comentada

Não. Ele deve depender apenas do contrato necessário para rastrear entregas, por exemplo IRastreamento.

Olhe pelo lado do consumidor

Um serviço que só consulta entregas deve receber IRastreamento, mesmo que um fornecedor também implemente IPagamento. Interfaces menores reduzem dependências entre clientes com necessidades distintas; contar métodos não é o critério.

D
Princípio 5

Dependency Inversion Principle

Princípio da Inversão de Dependência (DIP)

“Regras de negócio devem depender de abstrações, não de implementações concretas.”
D
Analogia: tomada e aparelho

Um aparelho foi projetado para um padrão de conexão, não para um modelo específico de extensão elétrica. Assim, o sistema pode trocar o componente conectado sem reconstruir a regra de negócio.

ANTES · implementação fixa
Trocar e-mail por SMS exige mexer no checkout.
public class CheckoutService
{
    private readonly EmailNotificador _email = new();

    public void Finalizar()
    {
        // ... regras do checkout ...
        _email.Enviar("Pedido finalizado");
    }
}
DEPOIS · dependência injetada
O checkout conhece apenas o contrato.
public interface INotificador
{
    void Enviar(string mensagem);
}

public class CheckoutService
{
    private readonly INotificador _notificador;

    public CheckoutService(INotificador notificador)
        => _notificador = notificador;

    public void Finalizar()
        => _notificador.Enviar("Pedido finalizado");
}
// Exemplo de criação:
// new CheckoutService(new EmailNotificador());
Quando usar?

Para integrar banco de dados, serviços externos, mensageria, pagamentos, notificadores e outros componentes substituíveis.

DIP ≠ injeção de dependência

DIP é o princípio de design. Injeção de dependência é uma técnica que ajuda a aplicá-lo; não exige framework.

Pergunta para a turma

Por que fica mais fácil testar CheckoutService quando ele recebe um INotificador?

Revelar resposta comentada

O teste pode fornecer um notificador falso que apenas registra mensagens, sem enviar e-mails reais e sem depender da rede.

Quem define a abstração?

O contrato deve expressar a necessidade da regra de negócio. Checkout e adaptadores dependem desse contrato; o adaptador implementa a necessidade do núcleo. Injetar EmailNotificador concreto é injeção, mas mantém a dependência concreta. Não é preciso um contêiner de DI.

02
Atividade prática

Laboratório de refatoração em C#

Construa um checkout extensível usando interfaces e estratégias. Atividade indicada para Console App (.NET 8 ou superior).

Projeto: Mini Loja SOLID

Use o projeto MiniLojaSolid ou cole o código em um Console App. O código inclui verificações executáveis com --test.

using System.Globalization;

CultureInfo.CurrentCulture = CultureInfo.GetCultureInfo("pt-BR");
// Ponto de composição: escolhe as implementações fora da regra de negócio.
var avisos = new NotificadorMemoria();
var checkout = new Checkout(new DescontoVip(), avisos);
var total = checkout.Finalizar(new Carrinho(200m));
Console.WriteLine($"Total: {total:C}");
Console.WriteLine(avisos.Mensagens[0]);

if (args.Contains("--test"))
{
    foreach (IPoliticaDesconto politica in new IPoliticaDesconto[]
             { new DescontoVip(), new DescontoBlackFriday() })
    {
        foreach (decimal entrada in new[] { 0m, 0.01m, 200m, 999m })
        {
            decimal saida = politica.Aplicar(entrada);
            Verificar(saida >= 0 && saida <= entrada, "Contrato do desconto");
        }
    }
    var fake = new NotificadorMemoria();
    var sut = new Checkout(new DescontoBlackFriday(), fake);
    Verificar(sut.Finalizar(new Carrinho(200m)) == 150m, "Black Friday: 150");
    Verificar(fake.Mensagens.Count == 1, "Uma notificação no sucesso");
    try
    {
        sut.Finalizar(new Carrinho(-1m));
        throw new Exception("Deveria rejeitar carrinho inválido");
    }
    catch (ArgumentOutOfRangeException) { }
    Verificar(fake.Mensagens.Count == 1, "Pedido inválido não notifica");
    Console.WriteLine("Verificações passaram.");
}

static void Verificar(bool condicao, string cenario)
{
    if (!condicao) throw new Exception($"Falhou: {cenario}");
}

public record Carrinho(decimal Total);

public interface IPoliticaDesconto
{
    // Entrada >= 0. Retorna valor entre 0 e a entrada.
    decimal Aplicar(decimal total);
}

public class DescontoVip : IPoliticaDesconto
{
    public decimal Aplicar(decimal total) => total * 0.90m;
}

public class DescontoBlackFriday : IPoliticaDesconto
{
    public decimal Aplicar(decimal total) => total * 0.75m;
}

public interface INotificador
{
    // Registra ou encaminha o aviso; não garante entrega ao destinatário.
    // Falhas do canal podem ser propagadas ao chamador.
    void Enviar(string mensagem);
}

public class NotificadorMemoria : INotificador
{
    public List<string> Mensagens { get; } = new();
    public void Enviar(string mensagem) => Mensagens.Add(mensagem);
}

public class Checkout
{
    private readonly IPoliticaDesconto _desconto;
    private readonly INotificador _notificador;

    public Checkout(IPoliticaDesconto desconto, INotificador notificador)
    {
        _desconto = desconto;
        _notificador = notificador;
    }

    public decimal Finalizar(Carrinho carrinho)
    {
        if (carrinho.Total <= 0)
            throw new ArgumentOutOfRangeException(nameof(carrinho));

        decimal total = _desconto.Aplicar(carrinho.Total);
        _notificador.Enviar("Pedido concluído");
        return total;
    }
}

Executar e verificar

dotnet run --project MiniLojaSolid
dotnet run --project MiniLojaSolid -- --test

Resultado inicial: R$ 180,00 e um aviso em memória. As verificações cobrem limites do desconto, Black Friday e ausência de notificação para total inválido. São exemplos de evidências; não provam todo o LSP. Valores monetários fracionários precisariam de uma política explícita de arredondamento em produção.

Missão 1 — OCPA classe DescontoBlackFriday já está no projeto para comparação. Crie DescontoAniversario com 15% e use-a sem editar Checkout. Para R$ 200,00, espere R$ 170,00.
Missão 2 — DIPCrie NotificadorSms : INotificador e troque a implementação na criação do checkout.
Missão 3 — SRPO checkout agora retorna o total; a apresentação fica no início do programa. Discuta se extrair a única validação traria benefício. Extraia um validador se as regras ganharem evolução própria.
Missão 4 — ISP e LSPExplique por que INotificador não deveria exigir GerarEtiqueta() e o que ocorreria se NotificadorSms.Enviar() sempre lançasse NotSupportedException.
Ver modelo de extensão para as missões 1 e 2

Black Friday já existe no projeto: não a duplique. Use-a como modelo para Aniversário (multiplicador 0.85m). Adicione o notificador SMS abaixo e escolha-o no ponto de composição. O envio é simulado no console.

public class DescontoBlackFriday : IPoliticaDesconto
{
    public decimal Aplicar(decimal total)
        => total * 0.75m;
}

public class NotificadorSms : INotificador
{
    public void Enviar(string mensagem)
        => Console.WriteLine($"SMS: {mensagem}");
}

// No início do Program.cs, substitua por:

Discutir a extração de validação na missão 3

Se a validação passar a mudar por regras próprias, esta extração é uma opção. Não é exigência do SRP criar uma classe para cada condição:

public class ValidadorCarrinho
{
    public void Validar(Carrinho carrinho)
    {
        if (carrinho.Total <= 0)
            throw new ArgumentException("Total inválido");
    }
}

Em Checkout, substitua o bloco if do método Finalizar por new ValidadorCarrinho().Validar(carrinho);. Como evolução opcional, receba também o validador pelo construtor para facilitar os testes.

Ver o raciocínio da missão 4

ISP: um notificador não é responsável por etiquetas; adicionar esse método à interface obrigaria implementações a oferecer uma operação irrelevante. LSP: quem recebe INotificador espera que Enviar seja uma operação utilizável. Uma implementação que lança sempre uma exceção não prevista rompe essa expectativa.

Discussão final: interfaces e classes extras são úteis quando representam diferenças reais. Em um programa minúsculo que nunca muda, abstrair tudo pode tornar o código desnecessariamente complexo.
