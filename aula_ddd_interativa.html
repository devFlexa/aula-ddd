1
Domain-Driven Design

Por que DDD?

Domain-Driven Design: o conhecimento do negócio orienta o modelo e o desenvolvimento.

Nosso cenário: uma loja de livros

Vendas confirma pedidos; Estoque reserva exemplares; Expedição prepara entregas. As equipes usam algumas palavras iguais, mas precisam de regras e informações diferentes. DDD ajuda a descobrir e expressar essas diferenças em colaboração com especialistas do negócio.

Pré-requisitos

Classes, encapsulamento, interfaces e coleções em C#. A aula de SOLID ajuda a discutir as dependências.

Objetivos de aprendizagem

  • Propor um vocabulário e limites para o modelo.
  • Distinguir entidades, valores e agregados.
  • Proteger invariantes e explicar eventos.
  • Executar e modificar um exemplo em C#.

Estratégia antes dos padrões

Design estratégico: entender subdomínios, contextos e relações. Design tático: expressar regras dentro de um contexto usando entidades, valores, agregados e serviços.

Um subdomínio é parte do problema de negócio. Um contexto delimitado é o limite em que um modelo se aplica. Os dois não são sinônimos nem precisam ter correspondência perfeita.

Subdomínios podem ser core (diferenciação), de suporte (operação específica) ou genéricos (necessidades comuns). Recomendações podem ser core para uma loja que compete pela curadoria; autenticação pode ser genérica. A classificação depende da estratégia.

DDD é útil para regras complexas e conhecimento em evolução. Em um cadastro simples, um modelo elaborado pode custar mais do que ajuda. DDD não exige microserviços, CQRS, Event Sourcing ou uma arquitetura específica.

Linguagem ubíqua

Um vocabulário compartilhado entre especialistas e desenvolvedores, dentro de um contexto.

↔

Analogia: a cozinha

“Pedido pronto” precisa ter significado consistente para quem cozinha e para quem serve. Ambiguidade produz erros mesmo quando cada pessoa cumpre sua tarefa.

“Confirmar pedido” significa concluir a compra, autorizar pagamento ou reservar estoque? A equipe precisa decidir. Nesta aula, significa fechar um pedido não vazio e impedir alterações nos itens. Pagamento e reserva estão fora dessa regra simplificada.

Modelo problemático
“Mudar status para 1” esconde a intenção e permite transições inválidas.
Modelo melhorado
“Confirmar pedido” expressa a intenção e executa regras acordadas.
// Antes: estado alterado sem intenção explícita
pedido.Status = 1;

// Depois: comportamento com significado de negócio
pedido.Confirmar();

A linguagem aparece nas conversas, testes, telas e código. Ela evolui conforme o time aprende; não é um glossário produzido uma vez e esquecido.

Exercício

Cancelar e estornar são a mesma operação?

Ver raciocínio
Não necessariamente. Cancelar pode encerrar um pedido; estornar pode devolver um pagamento. Descubra pré-condições, efeitos e responsáveis antes de unificar os termos.
3
Domain-Driven Design

Contextos delimitados

Bounded context: onde uma linguagem e um modelo têm significado consistente.

“Produto” tem diferentes sentidos

Catálogo

Título, autor e sinopse: como apresentar o livro?

Vendas

SKU e preço acordado: o que foi vendido e por quanto?

Estoque

SKU, saldo e reservas: quantos exemplares estão disponíveis?

Modelo problemático
Uma classe Produto global acumula regras de todas as equipes e torna as mudanças interdependentes.
Modelo melhorado
Cada contexto usa seu modelo. Identificadores e contratos explícitos relacionam informações entre contextos.

O preço do item do pedido é uma fotografia do acordo. Uma atualização no Catálogo não deve reescrever pedidos antigos.

Mapa de contextos

Registre quem fornece informações, quem depende de quem e como os contratos são traduzidos. Vendas consome uma oferta do Catálogo e mantém os dados necessários ao pedido. Uma camada anticorrupção pode traduzir códigos e estados de um legado para preservar o significado do modelo local.

Um contexto não é automaticamente um microserviço, banco ou processo. Um monólito modular também pode preservar esses limites.
Exercício

Alterar o endereço do perfil deve modificar uma entrega já expedida?

Ver discussão
Não por simples compartilhamento de objeto. O endereço da entrega representa um acordo em um momento. Perfil e Entrega podem ter modelos distintos; qualquer mudança depende de regra explícita da operação.

Domain-Driven Design

Entidades e objetos de valor

Identidade contínua e igualdade por atributos atendem a necessidades diferentes.

Entidade

Pedido

Continua sendo o mesmo pedido quando muda de estado. Dois pedidos com o mesmo total ainda são pedidos diferentes.

Objeto de valor

Dinheiro

É definido por valor e moeda. Dois valores de R$ 10 são equivalentes neste modelo. A imutabilidade evita mudanças inesperadas em consumidores.

public sealed record Dinheiro
{
    public decimal Valor { get; }
    public string Moeda { get; }
    public Dinheiro(decimal valor, string moeda)
    {
        if (valor < 0) throw new ArgumentOutOfRangeException(nameof(valor));
        if (moeda != "BRL") throw new ArgumentException("A loja opera em BRL.");
        Valor = valor;
        Moeda = moeda;
    }
}

O record fornece igualdade por valor; propriedades somente de leitura preservam a validação do construtor. A loja aceita apenas BRL e valores não negativos. Saldos devedores e múltiplas moedas exigiriam outras decisões.

Um ID de banco não transforma automaticamente um conceito em entidade. Pergunte se o negócio precisa distinguir e acompanhar aquela ocorrência ao longo do tempo.

Exercício

Uma linha do pedido precisa de identidade?

Ver decisão do exemplo
Aqui, cada linha é um valor imutável, sem ciclo de vida próprio. Se houver devoluções ou entregas parciais acompanhadas por linha, uma entidade ItemPedido com identidade pode ser mais adequada. O negócio orienta a escolha.

Domain-Driven Design

Agregados e invariantes

Um limite de consistência cuja raiz coordena as mudanças e protege as regras.

Pedido é a raiz do nosso agregado

Invariantes do exemplo: quantidades positivas; pedido não vazio ao confirmar; itens imutáveis após confirmação. Toda mudança passa pelas operações da raiz.

Modelo problemático
Itens públicos e Status com setter permitem confirmar pedidos vazios e alterar pedidos já confirmados.
Modelo melhorado
Métodos AdicionarItem e Confirmar validam a intenção antes de mudar o estado.
public void Confirmar()
{
    ExigirRascunho();
    if (itens.Count == 0)
        throw new InvalidOperationException("Pedido vazio não pode ser confirmado.");
    var total = Total;
    Status = StatusPedido.Confirmado;
    eventos.Add(new PedidoConfirmado(Id, total));
}

O projeto expõe a coleção com AsReadOnly() e usa itens imutáveis. Declarar apenas IReadOnlyList não protege uma lista mutável original se o consumidor puder recuperá-la por conversão.

Não inclua toda a loja no agregado. Defina seu limite pelas regras que precisam ficar consistentes juntas. Outros agregados podem ser referenciados por identidade.

Em um banco real, são necessárias transações e proteção contra concorrência. Encapsulamento não impede dois processos de sobrescreverem dados.
Exercício

Estoque deve fazer parte do agregado Pedido?

Ver discussão
Não automaticamente. Descubra se a reserva deve estar garantida antes da confirmação e qual equipe governa suas regras. Pode ser necessário um processo entre agregados ou contextos, com tratamento de recusa e compensação. O laboratório não promete disponibilidade de estoque.
6
Domain-Driven Design

Serviços, repositórios e eventos

Coordene o caso de uso mantendo as decisões de negócio no domínio.

Aplicação

Obtém o pedido, solicita confirmação e salva. Coordena dependências e, em um sistema real, autorização e transação.

Serviço de domínio

Expressa uma regra que não cabe naturalmente em entidade ou valor, como seleção de transportadora. Não é o destino de toda regra.

Repositório

Oferece acesso a agregados como coleção, escondendo armazenamento. Não é preciso um repositório para cada tabela.

public sealed class ConfirmarPedido(IPedidos pedidos)
{
    public void Executar(Guid id)
    {
        var pedido = pedidos.Obter(id)
            ?? throw new InvalidOperationException("Pedido não encontrado.");
        pedido.Confirmar();
        pedidos.Salvar(pedido);
    }
}

Comando pede; evento conta

ConfirmarPedido solicita uma ação que pode ser rejeitada. PedidoConfirmado representa um fato já ocorrido. O evento contém dados do fato, sem expor uma entidade mutável inteira.

Um evento de domínio pode ser tratado na própria aplicação. Para outro contexto, defina um contrato de integração e publique após a confirmação persistente. Uma outbox pode gravar estado e mensagem na mesma transação; consumidores ainda precisam lidar com reentregas, por exemplo usando idempotência.

Registrar eventos não significa usar Event Sourcing. Aqui o estado atual do pedido é usado pelo programa e os eventos são apenas uma lista em memória.

Exercício

O e-mail falhou após salvar o pedido. Devemos apagar a confirmação?

Ver discussão
Em geral, uma falha de notificação não desfaz um fato já confirmado. Defina repetição e entrega confiável conforme a necessidade. A lista de eventos em memória deste exemplo não oferece garantia de publicação ou entrega.

Resposta — limite de quantidade

Em AdicionarItem, valide antes de inserir:

if (quantidade <= 0 || quantidade > 10)
    throw new ArgumentOutOfRangeException(nameof(quantidade));

Verifique 10 aceito, 11 rejeitado e Itens/Total preservados na falha. A missão limita uma linha; limitar o total por SKU exige somar as linhas desse SKU.

Resposta — cancelamento
Inclua Cancelado no estado e uma operação Cancelar que exige rascunho. Use um contrato comum para armazenar PedidoCancelado e PedidoConfirmado na coleção de eventos. Verifique confirmação não cancelável, cancelamento repetido rejeitado e alterações bloqueadas. São regras da missão, não uma política universal.
Resposta — reserva de estoque
Um contrato pode carregar identificador único da solicitação, pedido e pares SKU/quantidade. O preço geralmente não é necessário. Defina um fluxo explícito, como AguardandoReserva antes de Confirmado, e trate recusa, expiração e mensagens duplicadas.

// Objeto de valor: imutável e comparado pelos valores. A loja usa apenas BRL.
public sealed record Dinheiro
{
    public decimal Valor { get; }
    public string Moeda { get; }
    public Dinheiro(decimal valor, string moeda)
    {
        if (valor < 0) throw new ArgumentOutOfRangeException(nameof(valor));
        if (moeda != "BRL") throw new ArgumentException("A loja opera em BRL.", nameof(moeda));
        Valor = valor;
        Moeda = moeda;
    }
}

// Neste modelo, a linha é um valor imutável; não possui ciclo de vida próprio.
public sealed record ItemPedido(string Sku, int Quantidade, Dinheiro PrecoUnitario);
public enum StatusPedido { Rascunho, Confirmado }
public sealed record PedidoConfirmado(Guid PedidoId, Dinheiro Total);

// Entidade e raiz do agregado: toda mudança passa por ela.
public sealed class Pedido
{
    private readonly List<ItemPedido> itens = new();
    private readonly List<PedidoConfirmado> eventos = new();
    public Guid Id { get; }
    public StatusPedido Status { get; private set; } = StatusPedido.Rascunho;
    public IReadOnlyList<ItemPedido> Itens => itens.AsReadOnly();
    public IReadOnlyList<PedidoConfirmado> Eventos => eventos.AsReadOnly();
    public Dinheiro Total => new(itens.Sum(i => i.PrecoUnitario.Valor * i.Quantidade), "BRL");
    public Pedido(Guid id)
    {
        if (id == Guid.Empty) throw new ArgumentException("Id obrigatório.", nameof(id));
        Id = id;
    }
    public void AdicionarItem(string sku, int quantidade, Dinheiro preco)
    {
        ExigirRascunho();
        if (string.IsNullOrWhiteSpace(sku)) throw new ArgumentException("SKU obrigatório.", nameof(sku));
        if (quantidade <= 0) throw new ArgumentOutOfRangeException(nameof(quantidade));
        ArgumentNullException.ThrowIfNull(preco);
        itens.Add(new ItemPedido(sku, quantidade, preco));
    }
    public void Confirmar()
    {
        ExigirRascunho();
        if (itens.Count == 0) throw new InvalidOperationException("Pedido vazio não pode ser confirmado.");
        var total = Total;
        Status = StatusPedido.Confirmado;
        eventos.Add(new PedidoConfirmado(Id, total));
    }
    private void ExigirRascunho()
    {
        if (Status != StatusPedido.Rascunho)
            throw new InvalidOperationException("Pedido confirmado não pode ser alterado.");
    }
}

public interface IPedidos
{
    Pedido? Obter(Guid id);
    void Salvar(Pedido pedido);
}

// Aplicação: coordena; a decisão de confirmar pertence ao agregado.
public sealed class ConfirmarPedido(IPedidos pedidos)
{
    public void Executar(Guid id)
    {
        var pedido = pedidos.Obter(id) ?? throw new InvalidOperationException("Pedido não encontrado.");
        pedido.Confirmar();
        pedidos.Salvar(pedido);
    }
}

// Infraestrutura didática: referências em memória, sem transações ou isolamento.
public sealed class PedidosEmMemoria : IPedidos
{
    private readonly Dictionary<Guid, Pedido> dados = new();
    public Pedido? Obter(Guid id) => dados.GetValueOrDefault(id);
    public void Salvar(Pedido pedido) => dados[pedido.Id] = pedido;
}
Os exemplos isolados anteriores são recortes didáticos. O código completo corresponde ao projeto. O repositório guarda referências em memória: não há banco, isolamento, rollback, controle de concorrência ou entrega confiável de eventos.

Quiz e revisão

Escolha uma alternativa por questão e confira a correção comentada.

Explique com suas palavras

Linguagem: significado compartilhado. Contexto: limite do modelo. Entidade: identidade no tempo. Valor: igualdade por atributos. Agregado: consistência protegida pela raiz. Evento: fato ocorrido.

Saída da aula: justifique um limite de contexto, uma invariante e uma escolha entre entidade e valor usando exemplos da loja.
